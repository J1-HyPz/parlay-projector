# Formula 1

How motorsport works in Parlay Projector, and — just as importantly — what it
does not claim.

## Why it needed structural work

Every other competition here is two sides and a score. `Game` had **required**
`home_team` and `away_team`, read in 58 places.

A Grand Prix has neither. Nominating two of twenty drivers to fill those slots
would have been a lie that leaked into notifications, the watchlist, parlay
labels and settlement. So the domain was widened instead:

```ts
home_team?: Team;      // absent for a race
away_team?: Team;
entrants?: Entrant[];  // the field, in classified order
session?: string;      // Practice 1, Qualifying, Race
title?: string;        // "Italian Grand Prix"
```

`sidesOf(game)` returns null for a race, so any code needing two sides has to
say what it does without them. That is what forced a real decision at each of
the 58 sites rather than a reflexive `!`.

## Provider

The same feed as every other competition — no new provider, no credentials, no
extra environment variables.

| Capability | Status |
| --- | --- |
| Season calendar | Full year, not hardcoded |
| Sessions | Practice 1–3, Sprint Shootout, Sprint, Qualifying, Race |
| Session status and start time | Per session, mapped to the shared statuses |
| Classified finishing order | Yes, with a winner flag |
| Driver standings | Yes — position, championship points, per-race scores |
| Constructor standings | Yes |
| Circuit, city, country | Yes |

**Not published, and therefore not modelled or displayed:**

lap times · gaps · per-race points · retirement status (DNF/DNS/DSQ flags) ·
lap counts · live timing · tyre data · pit stops · weather · sector times ·
practice pace as a distinct signal.

There is no bookmaker price for any motorsport market on this feed, so **every
F1 selection is `model_only`** — analysis, labelled as such, never presented as
a bet anyone has confirmed is available.

### One quirk that shapes the design

**An upcoming session publishes no entry list.** Verified live: the two
scheduled Grands Prix returned `field: 0`, while completed races returned full
finishing orders.

So the field for a race to come is taken from something that actually happened,
and the projection records which:

| `field_source` | Meaning |
| --- | --- |
| `session` | The session itself listed its entrants |
| `weekend` | Taken from a session already run this weekend |
| `recent` | Taken from the most recent completed race |

It is an assumption — that broadly the same drivers turn up — but it is an
assumption about observed people rather than an invented list, and it is stated
in the projection's data-quality reasons.

## Sessions

One `Game` per session, not per weekend. Sessions run on different days with
their own start times and statuses, so a day-based schedule needs them
separately — and someone looking at a Saturday wants qualifying, not a race two
days away.

Provider shorthand is normalised: `FP1` → Practice 1, `Qual` → Qualifying,
`SS` → Sprint Shootout. An unrecognised code falls back to the provider's own
text rather than being dropped.

Identity is the **session**, not the weekend: `espn-f1-<competitionId>`.

## The model

Nothing from the scoring model transfers. That one gives two sides an expected
score and compares samples. A race produces an *order*.

**Latent-strength order model.** Each driver carries a strength from where they
have actually finished; a simulated race gives every driver that strength plus
Gaussian noise and sorts the field. Ten thousand runs give the probabilities.

```
finishing positions ──► recency-weighted strength ──► + grid (if qualified)
                                  ↓
                     10,000 simulated finishing orders
                                  ↓
        win · podium · top 5 · points · head-to-head
```

- **Strength**: position converted to a 0–1 score, recency-weighted
  (half-life 5 races), then regressed toward the field average by how little is
  known. Two races is mostly the average driver; a full season is mostly
  themselves.
- **Grid**: applied only once qualifying has genuinely been run, at
  `gridWeight` 0.45.
- **Noise**: `raceNoise` 0.34 is the most consequential number here. Too low
  and the quickest car wins nine races in ten; too high and the model says
  nothing.

Every market comes off the same simulated orders, so they cannot contradict one
another — a driver's podium probability is necessarily at least their win
probability **by construction**, not by assertion. There is a test for it.

Simulation count is `PROJECTION_SIMULATIONS`, shared with the scoring model.

### What is not modelled, and why

**Reliability is not modelled separately.** The feed publishes a classified
order and nothing else, so a retirement is indistinguishable from a slow race.
It shows up in a driver's strength as a bad finish rather than as an explicit
DNF probability. Inventing a failure rate would be fabrication.

**No circuit-specific ratings.** Those need years of per-track history the
provider does not expose.

**Qualifying is not separately modelled.** A qualifying-pace model would need
practice timing, which is not published. Qualifying results are read (for the
grid) but not predicted.

## Markets

Two settlement rules cover everything:

```ts
{ kind: 'finish_position'; entrant: string; within: number }
{ kind: 'head_to_head'; entrant: string; over: string }
```

`within` 1 is the win, 3 the podium, 5 a top five, 10 a points finish.
Head-to-heads are generated between drivers **adjacent in the model's own
ranking**, so the pairing is genuinely close — a 95/5 match-up tells a reader
nothing.

Markets are generated for the eight strongest drivers only. A top-ten market on
the slowest car is arithmetically easy and of no interest.

## Parlays

Race legs travel through the ordinary `Selection` shape, so they reach the
optimiser, the store, settlement and the accuracy figures exactly like any
other leg. They combine freely with other sports.

**One leg per race.** Two markets on one Grand Prix are nearly the same bet —
a driver winning and the same driver on the podium — so the correlation group
is the session id and the optimiser takes at most one. This matches the
one-selection-per-game rule everywhere else.

Risk levels are not special-cased. All three accept race markets and the
**probability band does the separating**, which is why the split falls out
naturally:

| Level | Band | What qualifies |
| --- | --- | --- |
| Low | 70–95% | Points finish for a leading driver |
| Medium | 58–78% | Podium, top five, close head-to-head |
| High | 45–66% | Aggressive head-to-heads |

A race win sits nearer 30% and clears none of them. That is the honest answer,
not a gap — the model only offers what clears the bar.

## Settlement

Judged against the **classified finishing order**, frozen with the prediction.

| Case | Result |
| --- | --- |
| Classified inside the line | Won |
| Classified outside it | Lost |
| **Retired but classified** | **Lost** — it was tested and it failed |
| Not classified at all (withdrawal, non-start) | Void |
| Head-to-head, both classified | Compared |
| Head-to-head, either absent | Void |
| Race cancelled or abandoned | Void |
| No order published | Void |

A retirement losing rather than voiding is deliberate and matches how these
markets actually settle. The selection's own "what needs to happen" text says
so before the race, so it is not a surprise afterwards.

Corrections — penalties applied after the flag — go through the existing
finalisation window and audit trail, unchanged.

## Accuracy

Race predictions carry their own model version (`projection-v1-race`), so the
two models are never averaged together silently.

> They did not reach the tracker at all until 5 September 2026. The prediction
> store validated `selection_type` against a hand-written list that motorsport
> was never added to, so every F1 record was accepted, written, and then dropped
> on the next read — and erased from the file whenever anything else settled.
> The list is now derived from the type, so the omission cannot recur. They contribute to the
headline accuracy under the same eligibility rules as everything else: only the
final pre-race prediction counts, and only won/lost.

`actual` records the classified position and field size rather than a
scoreline, which is what the recent-results scroller reads to say
*"finished P6"*.

## Look-ahead protection

A projection made before qualifying must never see the grid. `gridFrom` takes
an `asOf` instant and returns null for a qualifying session that had not
started by then — the same guard the scoring model uses for results, and it is
tested directly.

## Caching

Race data uses the existing windows: settled history is cached for days, the
current window for hours. Two seasons of history (`historyDays` 700) are read
to rate drivers, chunked by the shared adapter.

## Configuration

**No new environment variables.** F1 uses the existing provider settings
(`ESPN_ENABLED`, `ESPN_CACHE_TTL_SECONDS`, `ESPN_TIMEOUT_MS`) and the shared
`PROJECTION_SIMULATIONS`. Nothing needs adding to the TrueNAS app.

## Limitations, stated plainly

- No live timing. There is no lap counter, no gap, no sector time, because none
  is published.
- No retirement, disqualification or non-start flags — only a classified order.
- No per-race points; the championship tables carry cumulative points only.
- No practice-pace signal, so a projection before qualifying rests on season
  form alone.
- No prices, so no market verification, no implied probability and no model
  edge for any race selection.
- Qualifying and sprint sessions are shown and used for the grid, but only the
  Grand Prix itself is projected.
